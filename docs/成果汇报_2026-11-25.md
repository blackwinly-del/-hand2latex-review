# Hand2LaTeX 工作台：交付说明与成果汇报

> 汇报日期：2026-11-25（第二版，含性能修复与证据缺口说明）
> 交付物：`Hand2LaTeX-1.0.0-win64.zip`（单个压缩包，**解压一次即可**，内含可运行程序 + 本文档）
> 负责范围：网页界面、桌面窗口外壳、启动与打包脚本、`workbench/app.py` 的缺陷修复
> （**识别内核未改动**，见第 5 节）

**拿到后怎么做**：解压 → 打开解压出来的文件夹 → 先读本文档 → 双击 `启动工作台.bat`。
压缩包里已经是完整的可运行程序，不需要再解压第二层。

## 1. 一句话结论

把「手写笔记照片转可编辑 LaTeX + 中文 PDF」这个流程，从一套需要装 Python、跑命令行、
自己看日志的开发环境，做成了**对方解压双击就能用的桌面程序**；这一轮修掉
**7 个真缺陷**（3 个后端 + 3 个启动/端口 + 1 个性能），并针对真实浏览器里
测出来的排版问题优化了界面。

需要说清楚的边界，分两句话讲，因为它们可信度不同：

- **整页转录没有逐字真值集**，所以对整页识别效果只做人工观察，**不做准确率承诺**。
- **单张公式裁剪图有 12 条用户逐条确认过的真值**，实测 66.7%（UniMERNet 单视角 8/12）。
  这个数字成立，但**样本只有 12 条，不能当泛化准确率**（详见 7.1）。

本次交付证明的是「流程能跑通、界面能用、关键故障已修」，不是「转录结果逐字正确」。

## 3. 这一轮修掉的 7 个真缺陷

全部用**真实运行**复现，不是读代码推测。每条都做了「修复前必现 → 修复后不复现」的对照。

| # | 缺陷 | 类型 | 用户会怎么感觉到 |
| --- | --- | --- | --- |
| ① | 上传全部失败留下孤儿目录 | 数据污染 | 列表里出现点不开的条目，每失败一次多一条 |
| ② | 只查扩展名不查文件头 | 错误归因 | 明显该说"这不是图片"，却报"请检查服务配置" |
| ③ | 并发编译互相覆盖 | 静默数据丢失 | 点了重新排版，PDF 变成别的版本，不报错 |
| ④ | 任务列表越用越慢 | 性能 | 没感觉，只觉得"这软件有点卡" |
| A | 端口探测失效（Windows） | 启动失败 | 服务起不来，或者起在想不到的端口 |
| B | 脚本端口检测同源问题 | 启动失败 | 同上 |
| C | 桌面模式不写 pid 文件 | 无法停止 | 点关闭说"没有服务在跑"，其实还在跑并占着端口 |

### 3.1 后端四个（`workbench/app.py`，经用户授权后修改）

#### ① 上传失败会在 `artifacts/jobs` 留下孤儿目录

- **现象**：上传后所有页都识别失败时，磁盘上留下一个只有源图、没有 `main.tex` 的目录。
  它会被任务列表扫到并当成正常任务返回，列表里出现打不开的条目；用户每失败一次多一条。
- **根因**：建目录、写源图在前，「全部页失败」的判定在后，中间没有清理。
- **修复**：目录建出后的整段包进 `try/except`，失败时 `_discard_job_directory()`。
  **只在目录里还没有 `main.tex` 时才删**——万一失败发生在很靠后的位置（tex 已落盘、
  编译才抛错），那个任务至少有代码可看，不该被当垃圾删掉。
- **顺便说明为什么没选另一种改法**：「先写临时目录、成功后再搬」看似更干净，
  但 `_attach_figure_sources` 会把**绝对路径**的 `source_image` 写进 `document.json`
  供 `\includegraphics` 使用，搬家会让这个路径指向已删除的临时目录，图形页静默变空白。
- **复验**：真实 HTTP 上传两张合法 PNG（全部页失败）后 `GET /api/jobs` 的 `total` 保持 0；
  原有的 10 个完整任务全部存活（确认没有误删）。

#### ② 上传只校验扩展名，不校验文件头

- **现象**：`echo "not an image" > fake.png` 能通过校验，一路走到识别阶段才失败。
- **影响**：返回的是 502「请检查服务配置」，把用户引向查密钥、查编译器，
  而真实原因是文件根本不是图片——排查方向完全跑偏，还白耗一次识别配额。
- **修复**：补 `_sniff_image_suffix`，校验 PNG / JPEG / WebP 文件头。
  WebP 特意同时看 `RIFF`（0-3）**和** `WEBP`（8-11）——只认 RIFF 不够，WAV 也用 RIFF。
  另补空文件检查。
- **顺带修的相关问题**：落盘后缀改用**识别出的真实格式**，不再用文件名后缀。
  所以叫 `.png` 其实是 JPEG 的文件会存成 `source.jpg`，格式与内容一致。
- **复验（在解压后的发行包上跑真实 HTTP）**：
  - 文本改名 `.png` → `400 这不是有效的图片文件（fake.png）：内容是 PNG / JPEG / WebP 之外的格式…`
  - 空文件 → `400 文件是空的（empty.png），请重新导出后再上传`

#### ③ 同一任务并发编译会互相覆盖，两个请求都报成功

- **现象**：并发两个编译请求，两个都返回 `200 + success:true`，但磁盘上只剩后写的那版。
  先到的那个请求拿到的是**假成功**。
- **影响**：前端网络重试、用户连点两下「重新排版」都可能触发。用户看到的是
  「点了重新排版，PDF 却变成了别的版本」，且没有任何错误提示，很难复现。
- **修复**：按 `job_id` 加锁（`_JOB_WRITE_LOCKS` + 一把元锁做惰性创建）。
  **元锁不能省**：没有它，两个线程可能同时发现「这个 job 还没锁」而各建一把，等于没锁。
  按问题文档里的提醒，**「代码没变就复用上次编译」的短路判断也移进了锁内**，
  否则并发下两个请求会同时判定「需要重新编译」。同样处理的还有另外 4 个写接口。
- **复验**：三路并发编译（三份不同内容），三个请求都 200，且**磁盘上的 PDF 内容与
  `main.tex` 一致**——判据用的是这个真正重要的事实，不是「都返回 200 就算过」。

#### 附带：把「全部页识别失败」的返回码从 502 改成 422

502 表示「服务端配置坏了」，422 表示「这次上传本身不成立」。全部页失败属于后者——
报 502 会把人引去查密钥和编译器。现在返回 422 并带逐页原因，界面能直接显示
「第几页、为什么」（见 4.1）。

#### ④ 任务列表越用越慢（性能缺陷，不是功能缺陷）

- **现象**：任务攒多以后，打开网页左侧列表明显卡顿。300 个任务时 `GET /api/jobs` 要 **2.2 秒**。
- **根因**：`_job_metadata` 里这样写：

  ```python
  metadata.setdefault("has_figures", _has_figure_blocks(directory))
  ```

  `setdefault` 的默认值参数是**先求值再传进去**的——即使 `job.json` 里早就写了
  `has_figures`，`_has_figure_blocks()` 照样执行一遍：对每个任务 glob 所有
  `page_*/document.json` 并逐个 `json.loads`。任务越多越慢，和磁盘无关，是纯浪费。
- **修复**：改成「键缺失时才算」。逻辑完全等价，只是不再白算。
- **复验**：300 个任务实测 **2198 ms → 447 ms（4.9 倍）**。
  拆开计时发现 `_has_figure_blocks` 一项就占了 2198 ms 里的 **1335 ms（61%）**，
  和"每个任务都要解析一遍 document.json"的判断吻合。
- **加了回归测试**：`test_job_metadata_does_not_recompute_has_figures_when_present`
  用 mock 断言「键已存在时 `_has_figure_blocks` 一次都不该被调用」，同时反向断言
  「键缺失时应该调用一次」——只测前者的话，把它改成永不调用也能通过。

> 这条值得单独说的原因：它不是"某个功能不好用"，而是**每次打开网页都在付费**，
> 而且随使用时长线性恶化。用户不会报这个 bug，只会觉得"这软件有点卡"。

### 3.2 启动侧三个（这是上一轮修的，列出以便完整对照）

| 缺陷 | 根因 | 修复 | 修复后实测 |
| --- | --- | --- | --- |
| **A 端口探测失效** | `desktop.py` 的 `_port_available` 用了 `SO_REUSEADDR`，**Windows 上语义和 Linux 相反**，能绑到别人正在监听的端口上还返回成功 | 改用 `SO_EXCLUSIVEADDRUSE` | 8770 被占时返回 `False`，自动落 8771，2.5 秒就绪 |
| **B 脚本端口检测同源问题** | `launch.ps1` 的 `Test-PortFree` 用 `TcpListener.Start()`，同样能误绑已占用端口 | 改成 `TcpClient.BeginConnect` 主动连一下 | 占用返回 `False`，空闲返回 `True` |
| **C 桌面模式不写 pid 文件**（最严重） | `desktop.py` 从不写 pid，而 `launch.ps1` 的 `Get-RunningServerProcess` **只认 pid 文件** | 新增 pid 写入/清理 | 服务 200 但 pid 文件不存在 → 现在 pid 写出且被识别、`-Stop` 真能停、退出后自动清理 |

缺陷 C 的后果很具体：用户点「关闭工作台」看到「没有正在运行的工作台服务」，
但服务其实还在跑还占着端口，于是再双击一次就又多一个进程。
排查时我机器上实际累积了 **5 个** `workbench.app` 进程，就是这个缺陷的累积证据。

关键细节：pid 文件写的是**子进程 uvicorn 的 pid**，不是桌面壳进程的——
`Get-RunningServerProcess` 会校验命令行里有没有 `workbench.app`，桌面壳进程过不了这个校验。
（这一条在解压后的发行包里复验过：pid 命令行确实是
`python.exe -m uvicorn workbench.app:app --host 127.0.0.1 --port 8877`。）

## 4. 这一轮的界面优化

上一轮把结构搭好了，这一轮修的是**真实浏览器里量出来的问题**，不是凭感觉调样式。

### 4.1 上传失败时，逐页原因摊在页面上

以前 `upload()` 的 `catch` 只做一件事：弹一条底部提示。后端 422 会带一段
「每一页都没能识别出来。第 1 页：xxx；第 2 页：yyy」，这段话塞进提示条后会被截断，
用户看不到「到底哪页、为什么」，只能反复重传。

现在：拆成逐页条目渲染成常驻面板（可关、下一轮上传自动清掉）；
拆不出页码的（比如「不是有效图片文件」）整段显示。
提示条同时改短，只说一句「这 2 页都没能识别出来，原因见页面上的说明」。
（第一版没改这句，截图里看到提示条把长文案又原样放了一遍、被省略号截断，属于重复信息。）

面板还会按原因给不同的下一步提示：所有页同一个原因 → 指向密钥/网络/配置；
逐页原因不同 → 指向照片光线和清晰度。

### 4.2 前端先拦明显不合规的文件，被拒的说清理由

以前拖入时会把非图片文件悄悄 `.filter()` 掉——用户拖 3 张、只识别 2 张，不知道为什么。
现在逐项检查（扩展名 / 空文件 / 单张 20 MB / 最多 10 页 / 整批 50 MB），
每个被拒的文件都说出文件名和理由。

### 4.3 缩略图按纸面比例留框

缩略图原来写死 `height: 178px`。手机拍的整页笔记是 893×1263（比例 0.71）的竖图，
塞进 214×178（比例 1.20）的横框里，图片被压成中间一条窄条、两侧大片空白——
而这一栏正是用来「对照原图核对」的。改成按 A4 比例留框后，实测图片填充率
从约 0.35 变成 1.0，手写内容能看清了。

### 4.4 窄屏下的四处排版问题

用真实浏览器在 1440 / 1366 / 1280 / 1180 / 1100 / 1024 六个宽度逐档量出来的：

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 右栏页签竖排 | 1280px 下「排版 / 问题 / 历史」被压成三个竖着的字柱 | 页签按钮禁止换行（中文默认可在任意两字间断行） |
| 右栏标题被截 | 1280px 下截成「预览与检」 | 标题允许省略但优先完整；≤1340px 收紧页签内边距；≤1100px 改两行（标题独占一行、页签在下） |
| 任务项断字 | 1024px 下「1 页失败」断成「1 页失」+「败」 | 允许按项折行，但每个小项不内部断字 |
| 横向溢出 52px | 1024px 下整页能横向拖动 | 侧栏 276→220px，三栏最小宽收紧 |

修完复测六个宽度：标题单行不截断、页签单行、任务项不断字、`scrollWidth - innerWidth = 0`。

## 5. 关于"内核没动"的说明（重要）

识别内核（`recognizer.py`、`reasoner.py`、`schemas.py`、`reasoning/`、
`workbench/full_page.py`、`workbench/fix.py`）**由另一位同事维护，本轮一行未改**。

仓库里有 `scripts/check_kernel.py` 做强校验。当前运行结果：

```
改动  recognizer.py           （同事在改，文件时间早于本轮所有改动）
一致  reasoner.py
一致  schemas.py
一致  reasoning/validators.py
一致  reasoning/context.py
一致  reasoning/render_check.py
改动  workbench/full_page.py  （同事在改，同上）
一致  workbench/fix.py
```

这两个文件的修改时间是 11-25 13:58，早于本轮所有改动（16:40 起）。
**我没有碰它们，也没有为了让校验变绿去回退**——如果内核确实推进了一版，
基线该由他更新，我改回去等于抹掉他的工作。

> 补充一个工程细节：用 `sha256sum` 直接校验在 Windows 上会有假报警。
> 因为 Git 默认 `core.autocrlf=true`，同一份代码 checkout 出来可能是 CRLF 也可能是 LF，
> 会有几个文件"永远对不上"，看着像被改了其实一个字没动。
> `check_kernel.py` 会先把行尾统一成 LF 再算哈希，结论才可信。

**本轮改了 `workbench/app.py`**：这个文件不在 `AGENTS.md` 的内核清单里，
且是在用户看到问题文档后明确要求「如果能改请帮我用力完善一下」之后改的。

> 说明：下面这轮是 2026-11-25 20:00 在最终交付包上重跑的，不是复用之前的结论。
> 因为包是重打的（含性能修复），旧结论不能直接沿用。

| 验证项 | 方法 | 结果 |
| --- | --- | --- |
| 从零解压可运行 | 解压到 `C:\tmp\` 独立目录后用随包 Python 起服务 | `/` 返回 **HTTP 200，98,386 字节**；`/api/status` 报 `build.source = 安装包`、`python 3.12.10` |

## 7. 证据边界：哪些还没做到 / 没证明

这一节请评审重点看，我不想让汇报显得比实际好。**7.2 和 7.3 是这一版新增的，
因为我在整理成果时发现原报告有一处说法不准确、以及一批引用的证据文件其实不存在。**

### 7.1 准确率：有一半指标，另一半没有

必须把两件事分开，混在一起说会让评审误判：

| 对象 | 有真值吗 | 实测结果 | 能不能写进汇报 |
| --- | --- | --- | --- |
| **单张公式裁剪图**（12 张） | 有，用户 2026-11-03 逐条确认 | UniMERNet 单视角 **8/12 = 66.7%** | 能，但必须同时说明样本只有 12 条 |
| **整页手写笔记** | **没有逐字真值** | 无 | **不能**，任何整页"准确率"都是编的 |

单张公式那组数据的四个配置对比（PP-FormulaNet-L 41.7% / plus-L 58.3% /
UniMERNet 66.7% / UniMERNet 多视角 58.3%）说明了两件事：换模型确实有效；
**多视角 + 上下文选择反而更差**（选择器把 sample_3 选成"补了括号"的版本、
把 sample_11 选成 `2^x`），所以画板默认走单视角——这是主动放弃了一个看起来更高级、
实际更差的做法，不是没做。

边界要说清楚：**这 12 条样本本身就是用来做模型选型的**，用同一批数据证明选型结果，
属于在同一批数据上自证。要拿它当泛化准确率，样本量至少得从 12 扩到 60 以上。
